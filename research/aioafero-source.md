# aioafero-source

**HEADLINE:** aioafero v9.3.0 (PyPI, Sep 15 2026; repo Expl0dingBanana/aioafero, Python >=3.12) gives typed async control of every device class the activation needs and just added opt-in Conclave TLS push, but it has NO Hubspace group/scene entities and NO client-side rate limiting — a Color Canopy scene change means ~200 individual PUTs (one per bulb) that our bridge must throttle and fan out itself.

## Findings
- [HIGH] **Current package identity: aioafero (formerly aiohubspace, formerly hubspace-async) at github.com/Expl0dingBanana/aioafero, PyPI 'aioafero' v9.3.0 released Sep 15 2026, MIT, Python >=3.12, maintained by Christopher Dohmen (Expl0dingBanana).**
  - PyPI shows 9.3.0 (Sep 15 2026), 9.2.1 (Sep 13), 9.2.0 (Sep 12), 9.1.0 (Sep 3), 9.0.1/9.0.0 (Aug 8-9), 8.0.0 (Aug 6), 7.0.x through Jan 1 2026 — roughly 17-21 releases in 2026 alone. Docs at aioafero.readthedocs.io. Older packages aiohubspace and hubspace-async are superseded; anything referencing aiohubspace is stale. Pin exact version for the install: 8.0.0 and 9.0.0 were breaking releases (8.0.0 reworked dual-channel lights + keyword-only set_state; 9.0.0 removed password auth from the bridge).
  - src: https://pypi.org/project/aioafero/ and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/CHANGELOG.rst
- [HIGH] **Auth is Keycloak OAuth2 + PKCE S256: host accounts.hubspaceconnect.com, realm 'thd', client_id 'hubspace_android', redirect_uri 'hubspace-app://loginredirect'; since v9.0.0 the bridge REQUIRES a refresh_token (no password login on the bridge), and initial login can hit an email-OTP challenge.**
  - src/aioafero/v1/auth.py + v1_const.py: auth endpoint /protocol/openid-connect/auth (response_type=code, scope='openid offline_access', code_challenge_method=S256), credential POST to /login-actions/authenticate (form fields username/password/credentialId plus session_code/execution/tab_id scraped from the kc-form-login HTML via BeautifulSoup; header x-requested-with: io.afero.partner.hubspace), token POST to /protocol/openid-connect/token. Refresh POST sends grant_type=refresh_token, scope='openid email offline_access profile', client_id=hubspace_android. If login returns a kc-otp-login-form page, an OTPRequired exception is raised and you complete via submit_otp(code) which POSTs field 'emailCode'. TokenData persists to disk via to_session_dict()/from_session_dict(). Operational consequence for the 5 vignette accounts: perform initial logins and capture refresh tokens BEFORE install week (on-site logins from a new IP may trigger email OTP), then run kiosks from stored refresh tokens.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py
- [HIGH] **Token lifecycle: access token expiry taken from Keycloak's expires_in minus a 2s buffer, with a 118s fallback (DEFAULT_TOKEN_TIMEOUT=118, TOKEN_EXPIRY_BUFFER=2); token() is guarded by a single asyncio.Lock so 200 concurrent requests won't stampede Keycloak, but they do all serialize briefly through that lock per request.**
  - Verbatim from auth.py: `DEFAULT_TOKEN_TIMEOUT: Final[int] = 118`, `TOKEN_EXPIRY_BUFFER: Final[int] = 2`, `async def token(...): async with self._async_lock:`. create_request() in v1/__init__.py awaits self._auth.token() on every API call and injects 'Authorization: Bearer {token}'. During an actual refresh (~hundreds of ms) all in-flight request creation blocks — a small, bounded latency spike that could land mid-scene-change; pre-warming the token right before Apply is a cheap mitigation in our bridge.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py
- [HIGH] **Complete REST surface (client 'hubspace'): auth on accounts.hubspaceconnect.com; account id from api2.afero.net GET /v1/users/me; everything device-related on semantics2.afero.net — GET /v1/accounts/{acct}/metadevices?expansions=state,capabilities,semantics (discovery), GET /v1/accounts/{acct}/metadevices/{id}/state (per-device state), PUT same path (set state), GET /v1/accounts/{acct}/devices/{id}/versions (firmware, every 6h); Conclave access via POST api2.afero.net /v1/accounts/{acct}/conclaveAccess.**
  - v1_const.py verbatim: AFERO_CLIENTS['hubspace'] = {API_DATA_HOST: 'semantics2.afero.net', API_HOST: 'api2.afero.net', AUTH_DEFAULT_CLIENT_ID: 'hubspace_android', AUTH_DEFAULT_REDIRECT_URI: 'hubspace-app://loginredirect', AUTH_OPENID_HOST: 'accounts.hubspaceconnect.com', AUTH_REALM: 'thd'}. User-Agent template: 'Mozilla/5.0 (Linux; Android 15; ${client_name} Build/test; wv) AppleWebKit/537.36' (client_name default 'aioafero'). Discovery adds units=fahrenheit param when configured. These are the exact hostnames to whitelist/QoS on the dedicated venue network.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py
- [HIGH] **Set-state wire format: PUT /v1/accounts/{acct}/metadevices/{metadevice_id}/state with JSON {'metadeviceId': id, 'values': [{'functionClass', 'functionInstance', 'value', 'lastUpdateTime'}...]}; one PUT per device only — the payload carries a single metadeviceId, so there is no multi-device batch write in this API as used by the library.**
  - controllers/base.py update() flow: dataclass_to_afero() diffs desired features against cached state (skipping no-ops unless send_duplicate_states=True), features emit via iter_afero_values(), then a single PUT with content-type 'application/json; charset=utf-8'. Response 'values' are filtered back into the cache and emitted as RESOURCE_UPDATE_RESPONSE events, so the library's cache updates optimistically from the PUT response without waiting for the next poll. Multiple functionClasses for ONE bulb (power + brightness + color-rgb + color-mode) can ride in one PUT via LightController.set_state — use that, not sequential calls. For the canopy: a 5-zone scene = 40-200 PUTs; the kiosk bridge must implement its own concurrency window (the library provides none) and per-zone ordering.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/base.py
- [HIGH] **RGB light payload specifics: power = functionClass 'power' (value 'on'/'off'; 'toggle' for per-channel), brightness = 'brightness' (int percent, functionInstance selects channel 'primary'/'color'/'white'/zone), RGB = 'color-rgb' with value {'color-rgb': {'r': 0-255, 'g': 0-255, 'b': 0-255}}, color temp = 'color-temperature' (numeric string, model-dependent optional suffix via a 'prefix' field — some bulbs expect e.g. '3000K'), mode = 'color-mode' ('color'/'white'/'sequence'/'night-light', dual-channel 'mixed'), effects = 'color-sequence' (functionInstance 'preset' plus a per-group instance).**
  - From controllers/light.py + models/features.py verbatim api_value shapes. LightController methods: turn_on/turn_off, set_brightness, set_color_temperature, set_rgb(device_id, r, g, b), set_effect, set_white, and omnibus set_state(device_id, *, on, temperature, brightness, color_mode, color, effect, ...). Setting RGB requires color-mode='color' on many bulbs — set_state handles mode+color together; 'no-brightness' modes apply color-mode before power on turn-on. Multizone string lights arrive as split clones (one Light resource per zone) sharing a parent metadevice; split-device poll fix landed 9.2.1 (Sep 13 2026). ITEM_TYPES=[ResourceTypes.LIGHT] filtered from metadevices with typeId 'metadevice.device'.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/models/features.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/light.py
- [HIGH] **NO first-class Hubspace GROUPS or SCENES: ResourceTypes has no scene/group member, discovery keeps only typeId=='metadevice.device' (rooms 'metadata.room' and homes 'metadata.home' exist in the enum but are filtered out of controllers), there is no scene/group controller or docs page, and the HA integration README doesn't surface scenes either.**
  - models/resource.py enum: DEVICE='metadevice.device', HOME='metadata.home', ROOM='metadata.room', plus device classes light, power-outlet, door-lock, fan, switch, landscape-transformer, water-timer, thermostat, security-system(-keypad/-sensor), portable-air-conditioner, dehumidifier, exhaust-fan, unknown. event.py discovery filter verbatim: `if dev.get("typeId") == ResourceTypes.DEVICE.value and dev.get("description", {}).get("device", {}).get("deviceClass")`. Consequence: any scene the official Hubspace app stores server-side is invisible/untriggerable through aioafero — the kiosk must implement scenes client-side as per-bulb fan-out, OR we MITM the official app (the repo ships MITM capture docs at docs/ + 'Add MITM capture docs' commit Jul 25 2026) to find Afero's server-side scene-execution endpoint, which would collapse a 200-PUT scene change into one call if it exists.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/models/resource.py
- [HIGH] **Polling design: EventStream runs three asyncio loops — discovery (default 3600s), state polling (default 30s), and an event queue processor. Each state-poll cycle issues ONE GET per metadevice for ALL tracked devices concurrently via asyncio.gather with NO semaphore — with ~200 bulbs on one account that is a 200-request HTTPS burst every 30 seconds.**
  - Verbatim from v1/__init__.py _fetch_all_device_states: builds active metadevice id set, `tasks = [self._fetch_device_states(mid) for mid in active_ids]; results = await asyncio.gather(*tasks, return_exceptions=True)`. Loop error backoff verbatim: `backoff_time = min(attempt * self.polling_interval, 600)` with DISCONNECTED/RECONNECTED events — so after an internet cut, first retry is ~30s (fits the <60s recovery target only if the first retry succeeds; second attempt waits 60s). Per-device 403 tracking: after STATE_FETCH_FORBIDDEN_LIMIT=3 consecutive Forbidden responses a device's state polls pause until the next successful discovery (feature added Aug 9 2026). For the canopy, consider polling_interval >= 60s or Conclave push to cut poll load, since Apply-confirmation can come from PUT responses instead.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/event.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py
- [HIGH] **Rate limiting/backoff is minimal and reactive only: request() retries at most MAX_RETRIES=3 with sleep 0.25s*attempt on HTTP 429/503/504, then raises ExceededMaximumRetries; 403 raises immediately; there is no proactive client-side throttle, no request semaphore, and no queueing — sustained 429s during a 200-PUT scene change would surface as failed bulbs.**
  - Verbatim from v1/__init__.py request(): `while retries < v1_const.MAX_RETRIES: ... if retries > 1: retry_wait = 0.25 * retries; await asyncio.sleep(retry_wait); ... if resp.status in [429, 503, 504]: continue; if resp.status == 403: raise web_exceptions.HTTPForbidden`. Total worst-case retry budget is ~0.75s over 3 attempts — far too thin for a burst of 200 writes if Afero throttles per-account. Our bridge MUST wrap send_service_request/set_state in its own bounded-concurrency executor (e.g. semaphore of 10-25 in flight, per-zone waves) and treat ExceededMaximumRetries as a re-send trigger to meet 'zero wrong/missed bulbs across 100 scene changes'.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py
- [HIGH] **Real-time push exists but is 4 days old: v9.3.0 (Sep 15 2026) added an opt-in Conclave client (enable_conclave=True) — raw TCP+TLS (NOT websocket) to a host/port obtained from POST /v1/accounts/{acct}/conclaveAccess, JSON frames, server-driven heartbeats, 1s→60s doubling reconnect backoff, and REST true-up on reconnect.**
  - conclave/access.py: POST body {'user': bool, 'softHub': bool}; response parsed for conclave.host/port/ssl(default True)/compression(default True) plus a 'short-lived single-use Conclave socket access token' (tokens[].token, channelId=account UUID, expiresTimestamp), preferring token type 'account'. conclave/client.py: asyncio.open_connection with SSL context + server_hostname, opening handshake '{}' then login frame; DEFAULT_READ_TIMEOUT=75.0s, WIRE_IDLE_HEARTBEAT_MULTIPLIER=2.0, heartbeat interval taken from server handshake, acks are bare newline; private frames = device state updates (handled serially under a lock), public frames = inventory add/delete; on reconnect it calls fetch_all_device_states() and regenerates events. Bridge starts Conclave only after the first REST discovery poll. The jdeath HA integration now treats REST polling as a 15-minute true-up when push is active. For the kiosk, push gives fast external-change awareness, but its maturity at 200 devices is unproven — do not make the show depend on it before the bench gate.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/client.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/access.py
- [HIGH] **All four vignette device classes are supported with exact function classes: locks via 'lock-control' (LOCKING/UNLOCKING enum; LockController.lock/unlock), smart plugs/outlets via SwitchController ('power'/'toggle', functionInstance keys for multi-outlet; matches ResourceTypes SWITCH, POWER_OUTLET, LANDSCAPE_TRANSFORMER), ceiling fans via FanController ('power', 'fan-speed' percentage mapped to the model's ordered speed list, 'fan-reverse', 'comfort-breeze' preset toggle), and string lights as LIGHT-class devices (multizone ones appear as split per-zone Light resources).**
  - AferoBridgeV1 instantiates 13 controllers: dehumidifiers, devices, exhaust_fans, fans, lights, locks, portable_acs, security_systems (+keypads +sensors), switches, thermostats, valves (water-timer). Humidifier for vignette 3: dehumidifier controller landed Sep 12 2026 (contributed PR); a plain humidifier likely rides the same platform — verify the actual SKU's deviceClass at bench. Defiant locks: only lock/unlock control, no code management. Fountain on outdoor smart plug = SwitchController.turn_on(device_id, instance=...).
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/switch.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/lock.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/fan.py

## Numbers
- aioafero current version / release date = **9.3.0 / Sep 15 2026 (Python >=3.12, MIT)** (https://pypi.org/project/aioafero/)
- Default state polling interval (per-account, all devices) = **30 s (constructor polling_interval; discovery_interval 3600 s; firmware version poll 21600 s)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py)
- State-poll fan-out per cycle = **1 GET per metadevice, all concurrent via asyncio.gather, no semaphore (200 bulbs = 200-request burst/30s)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py)
- HTTP retry policy = **MAX_RETRIES=3, sleep 0.25s*attempt, retry only on 429/503/504, then ExceededMaximumRetries; 403 raises immediately; 3 consecutive 403s pause that device's polls** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py)
- Polling-loop failure backoff = **min(attempt * polling_interval, 600) s — first retry ~30s after an outage with defaults** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/event.py)
- Access-token expiry fallback / refresh buffer = **118 s default (DEFAULT_TOKEN_TIMEOUT) when Keycloak omits expires_in; TOKEN_EXPIRY_BUFFER 2 s; refresh under one asyncio.Lock** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py)
- Conclave push client timing = **read timeout 75 s, idle heartbeat multiplier 2.0, reconnect backoff 1 s doubling to 60 s max; added in 9.3.0 (Sep 15 2026)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/client.py)
- RGB value ranges on the wire = **color-rgb r/g/b 0-255; brightness integer percent (1-100); color-temperature numeric string, model-dependent suffix** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/models/features.py)
- 2026 release count / breaking majors = **~17-21 PyPI releases Jan-Sep 2026; breaking majors 7.0.0 (Jan 1), 8.0.0 (Aug 6), 9.0.0 (Aug 8)** (https://pypi.org/project/aioafero/#history)
- HA integration REST true-up when push active = **900 s (15 min) default** (https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md)

## Bench tests
- Burst-write ceiling: from one account, fire concurrent PUT /v1/accounts/{acct}/metadevices/{id}/state to 40 real bulbs (one zone), then 200, at concurrency windows of 10/25/50/unbounded; record HTTP 429/503 counts, completion time, and whether aioafero's 3x0.25s retry ladder absorbs them — this directly determines the semaphore size our bridge needs and whether 5 separate accounts (one per zone) raise the ceiling.
- Latency distribution: instrument Apply -> PUT sent -> bulb visibly changes for each of 200 bulbs across 100 scene changes; verify 95% <2s start, first-to-last spread <2s, full scene <5s; compare one combined PUT per bulb (power+brightness+color-rgb+color-mode in a single values[] array) vs sequential single-value PUTs.
- Poll-load interaction: run the default 30s EventStream polling on the 200-bulb account WHILE executing scene changes; check whether the 200-GET poll burst steals bandwidth/attracts throttling that delays writes; retest with polling_interval=120s and with polling disabled (PUT-response-driven cache only).
- Conclave soak: enable_conclave=True on v9.3.0 with the full 200-device inventory for 8+ hours behind the venue-style NAT; log CONCLAVE_DISCONNECTED/RECONNECTED events, heartbeat stability, memory/queue growth, and whether private frames keep up during rapid scene changes; then hard-cut WAN for 5 minutes and confirm REST true-up + push recovery completes <60s after internet returns.
- Auth resilience: provision all 5 vignette accounts' refresh tokens off-site first; then on the venue network do a cold login to confirm whether Keycloak (accounts.hubspaceconnect.com, realm thd) triggers the email-OTP path (kc-otp-login-form) from a fresh IP; also measure token refresh time and verify no scene-change stalls when the asyncio.Lock'd refresh fires mid-burst (force by setting token_expiration in the past).
- Wire-format edge cases on the actual EcoSmart A19 SKU: confirm color-temperature value format (plain '3000' vs suffixed '3000K') from the discovery capability definitions; confirm color-mode must be set to 'color' for color-rgb to take effect from white mode; measure whether identical repeated states are dropped by dataclass_to_afero (need send_duplicate_states=True for our idempotent re-send strategy).
- MITM the official Hubspace Android app (repo's docs include MITM capture instructions) while creating/applying a 40-bulb group scene: capture whether Afero exposes a server-side group/scene-execution endpoint that applies one command to many devices — if it exists, one call could replace 200 PUTs and trivially beat the 2s spread target.

## Open questions
- What are Afero cloud's actual per-account/per-IP write rate limits (429 thresholds) on semantics2.afero.net? The library encodes no limits, HA users poll at 30s+ scale of ~10-50 devices — nobody publicly runs 200 devices on one account; this is the single biggest unknown for the canopy.
- Does the Afero platform have a server-side scene/group execution endpoint (used by the official app's Groups/Scenes) that aioafero simply doesn't wrap? metadevices discovery filters to typeId 'metadevice.device' but the API also returns 'metadata.room'/'metadata.home' — what other typeIds (scene? group?) exist in the raw expansions=semantics payload for an account with app-created groups?
- How stable is the 4-day-old Conclave client (9.3.0) at 200 devices — does the per-account channel (channelId=account UUID) deliver per-device state frames at scene-change rates without falling behind, and what is the conclaveAccess token renewal story for multi-day uptime?
- What is the real Keycloak expires_in for hubspace_android tokens (the 118s constant is only a fallback) — i.e., actual refresh cadence under an 8h soak?
- Do PUT state responses constitute confirmation the BULB changed, or only that the cloud accepted the value (device could be offline)? Need to determine whether 'zero wrong bulbs' verification requires readback polling or Conclave private frames per bulb.
- Are there per-device write serialization rules (does a second PUT to the same metadevice while one is in flight get dropped/merged by the cloud, and does lastUpdateTime skew matter)?
