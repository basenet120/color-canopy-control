# app-reverse-eng

**HEADLINE:** The Hubspace protocol is fully mapped publicly (Keycloak PKCE auth, semantics2 metadevice REST, Conclave TLS push, encrypted BLE onboarding) and is 100% cloud with no local control path — but no public capture shows whether the app's group/scene apply is one server-side call or N per-device calls; the legacy Afero platform has a one-call server-side rules-execute primitive, and one mitmproxy session of the app controlling a 40-bulb group is the decisive missing experiment.

## Findings
- [HIGH] **The community reverse-engineered stack is consolidated in Expl0dingBanana/aioafero (renamed from aiohubspace; predecessor hubspace_async), currently v9.3.0 released 2026-09-15, and it is the engine behind jdeath/Hubspace-Homeassistant; all older projects (hubspace-ng, sajmonr/homebridge-hubspace, jan-leila/hubspace-py, zenion, ctrlcmdshft fork, kirchmeyer/matterbridge-hubspace) document the same API surface.**
  - aioafero exposes typed controllers over 'AferoBridgeV1'; it is actively maintained (releases within the last week as of Sep 19 2026) and now includes a Conclave push client and mitmproxy documentation for capturing the official app. The repo's tests ship a real anonymized account dump (tests/v1/data/raw_hs_data.json) showing metadevice typeIds: metadevice.home, metadevice.room, metadevice.device only.
  - src: https://github.com/Expl0dingBanana/aioafero and https://pypi.org/project/aioafero/
- [HIGH] **Auth is Keycloak OAuth2 Authorization Code + PKCE (S256) against accounts.hubspaceconnect.com, realm 'thd', public client_id 'hubspace_android', redirect_uri 'hubspace-app://loginredirect'; endpoints are /auth/realms/thd/protocol/openid-connect/auth, /auth/realms/thd/login-actions/authenticate (HTML form POST of username/password), and /auth/realms/thd/protocol/openid-connect/token; initial scope 'openid offline_access', refresh scope 'openid email offline_access profile'; access tokens are treated as living ~118 seconds so everything runs on refresh tokens.**
  - Verbatim from aioafero src/aioafero/v1/v1_const.py and v1/auth.py: AFERO_CLIENTS['hubspace'] = {API_DATA_HOST: 'semantics2.afero.net', API_HOST: 'api2.afero.net', AUTH_DEFAULT_CLIENT_ID: 'hubspace_android', AUTH_DEFAULT_REDIRECT_URI: 'hubspace-app://loginredirect', AUTH_OPENID_HOST: 'accounts.hubspaceconnect.com', AUTH_REALM: 'thd'}. PKCE verifier = 40 random bytes base64url; DEFAULT_TOKEN_TIMEOUT=118s with 2s expiry buffer. The login flow scrapes the Keycloak login form action URL then exchanges the code; no client secret.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py
- [HIGH] **A specific Android-webview User-Agent is used to avoid Afero-side filtering: 'Mozilla/5.0 (Linux; Android 15; ${client_name} Build/test; wv) AppleWebKit/537.36 (KHTML, like Gecko) Version/4.0 Chrome/138.0.7204.63 Mobile Safari/537.36', and requests explicitly set a 'host' header (semantics2.afero.net for state calls, api2.afero.net for platform calls).**
  - The UA template lives in AFERO_GENERICS['DEFAULT_USERAGENT']; controllers/base.py sets headers {'host': API_DATA_HOST, 'content-type': 'application/json; charset=utf-8'} on state PUTs. The library also hardcodes MAX_RETRIES=3 and pauses per-device state polling after 3 consecutive 403s (STATE_FETCH_FORBIDDEN_LIMIT), which is direct evidence Afero serves 403s to clients it dislikes — treat UA and pacing as load-bearing.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py
- [HIGH] **Device/API surface: GET https://semantics2.afero.net/v1/accounts/{accountId}/metadevices (optionally ?expansions=state) lists everything; state writes are PUT https://semantics2.afero.net/v1/accounts/{accountId}/metadevices/{deviceId}/state with body {'metadeviceId': id, 'values': [{'functionClass', 'functionInstance', 'value', 'lastUpdateTime'}...]} — multiple attributes per bulb batch into ONE PUT, but each PUT addresses exactly ONE metadevice; account id comes from GET api2.afero.net/v1/users/me.**
  - One PUT can set power+color-mode+RGB+brightness together for one bulb (states list), so a 40-bulb zone change is 40 HTTP PUTs in the community stack, not 160 — but still N calls fanned out from the client. The current Flutter app hits a /v2/ variant (semantics2 '/v2/accounts/<account>/metadevices/<id>/state' per the Sep 2026 native teardown, and both '/v1/accounts/' and '/v2/accounts/' string constants exist in the app binary) while aioafero still successfully uses /v1/. Multi-function devices split into child metadevices with suffixed ids ('-light', '-fan').
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/base.py and https://github.com/go-go-golems/go-go-parc/blob/main/Projects/2026/09/05/PROJ%20-%20Hubspace%20BLE%20-%20From%20Bluetooth%20Packets%20to%20Cloud%20Control.md
- [MEDIUM] **CRITICAL QUESTION status — no public capture proves how the official app applies a scene/group; but three hard facts bound the answer: (1) the community write path is strictly N per-device cloud PUTs; (2) the Afero platform has a server-side account rules engine where one Rule holds deviceActions for MANY devices and is executed server-side by a single POST /v1/accounts/{accountId}/rules/{ruleId}/actions with body {'type':'execute_actions'}; (3) the current Hubspace Flutter app's SDK (afero_dart_sdk) contains an 'AferoClientSceneMixin' and 'AferoClientFavoritesMixin', proving scenes are first-class API entities in the shipping app, not client-side loops over the metadevice PUT.**
  - The rules primitive is in Afero's own open-source AferoJavaSDK: GET /v1/accounts/{accountId}/rules?expansions=schedule, POST /v1/accounts/{accountId}/rules (Rule = {deviceActions: [{deviceId, attributes: [{id, value}], durationSeconds}], deviceFilterCriteria, schedule/scheduleId, deviceGroupId, enabled}), and ruleExecuteActions POST returning ActionResponse[]. RuleExecuteBody is literally {'type': 'execute_actions'}. The Rule model even carries a deviceGroupId field. Whether the hubspace_android Keycloak token authorizes these api2.afero.net rules endpoints, and whether the app's Groups feature uses them versus N v2-semantics PUTs, is unverified — no public repo references a Hubspace scenes endpoint ('metadevice.scene' and 'AferoClientSceneMixin' each return zero/one GitHub code hits, the one being the decompile itself). This is bench-test #1.
  - src: https://raw.githubusercontent.com/aferodeveloper/AferoJavaSDK/master/afero-sdk-client-retrofit2/src/main/java/io/afero/sdk/client/retrofit2/api/AferoClientAPI.java and https://raw.githubusercontent.com/aferodeveloper/AferoJavaSDK/master/afero-sdk-core/src/main/java/io/afero/sdk/client/afero/models/DeviceRules.java and https://raw.githubusercontent.com/wesen/2026-09-05--inspect-hubspace/main/sources/hubspace-dart/metadata/afero_client.dart
- [HIGH] **Realtime state is NOT a websocket: it is 'Conclave', a raw TLS TCP socket speaking newline-delimited JSON with optional zlib compression; the client POSTs api2.afero.net/v1/accounts/{accountId}/conclaveAccess {'user': true, 'softHub': false} to receive {host, port, token, channel_id} (e.g. conclave-stream1.afero.net; official SDK default conclave-stream.afero.io:443), then sends a login frame and receives 'attr_change' and 'status_change' private events plus bare-newline heartbeats.**
  - Both the official AferoJavaSDK (ConclaveClient.java: DEFAULT_HOST 'conclave-stream.afero.io', DEFAULT_PORT 443, login/say/whisper messages, ERROR_CODE_INVALID_TOKEN 906) and aioafero's conclave module (handshake→login→welcome, heartbeat ack, read timeout 75s or 2x server heartbeat, reconnect backoff 1s→60s doubling, REST reconciliation on reconnect) agree. Conclave attr_change events carry raw numeric attribute ids that must be mapped per-device-profile via each metadevice's description.functions[].values[].deviceValues[].key — the semantic (functionClass/functionInstance) and raw-attribute models are two views of the same state. jdeath's HA integration ships Conclave push enabled by default since the 'dev-conclave-support' release, with REST polling demoted to a 900s true-up — this is the kiosk's state-feedback channel.
  - src: https://raw.githubusercontent.com/aferodeveloper/AferoJavaSDK/master/afero-sdk-core/src/main/java/io/afero/sdk/conclave/ConclaveClient.java and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/client.py and https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md
- [HIGH] **BLE onboarding was reverse-engineered in depth in September 2026 (go-go-golems/wesen project): bulbs expose GATT service 7a5a0068-6469-7545-4c42-6e6162696b with characteristic pairs 7a5afe01/02 (setup), 7a5afffb/fc (negotiation), 7a5afffd/fe (encrypted messaging), 7a5afe03/04 (ack/credit); the session is ECDH-derived AES-128-GCM (12-byte nonce, truncated 6-byte tag), envelope 'u16le len | u32le seq | ciphertext | tag[6]', inner frame 'u16le length | u8 type | u8 flags | u16le attribute_id | u16le value_length | value'.**
  - The phone acts as an Afero 'softhub' (io.afero.hubby JNI wrapper around native libhubsy.so, Flutter platform channel 'afero.io/softhub_method'): provisioning APIs are getWifiSSIDListFromHub(deviceId) → bulb scans and returns SSID list over the encrypted BLE session, sendWifiCredentialToHub(deviceId, ssid, password), requestSetupModeAction + SecondFactor for secure association, and WIFI_SETUP_STATE_ATTRIBUTE tracks progress — i.e., Wi-Fi credentials go phone→BLE→bulb, but association/authorization round-trips through the cloud. Practical consequence for a 200-bulb install: onboarding requires the app + live internet per bulb, there is no documented offline/batch provisioning, and moving to a new SSID means re-onboarding every bulb (plan install-week Wi-Fi SSID/password to exactly match what bulbs were provisioned with).
  - src: https://github.com/go-go-golems/go-go-parc/blob/main/Projects/2026/09/05/PROJ%20-%20Hubspace%20BLE%20-%20From%20Bluetooth%20Packets%20to%20Cloud%20Control.md and https://raw.githubusercontent.com/wesen/2026-09-05--inspect-hubspace/main/sources/hubspace-app/java/io/afero/hubby/Hubby.java
- [HIGH] **There is NO usable local-network or BLE control path post-setup: the Sep 2026 native/BLE investigation concluded 'Internet-independent smart control is not demonstrated' — the phone can relay pre-encrypted payloads over BLE but cannot construct/authorize commands offline, Afero's own docs describe the mobile app as an internet gateway ('hub') for BLE products, and the community consensus (jdeath README: Hubspace is '100% reliant on the cloud', updates slow) matches; hobbyists wanting local control physically replace the Afero radio board with an ESP32 (dresslerc/esphome-afero).**
  - The BLE writeup's status: 59 captured envelopes reconstructed, crypto model validated, but 'The light is not yet independently controlled offline' and session-key extraction remains unsolved — so for the Oct 20-23 install, treat BLE as onboarding-only and plan for hard cloud dependency (the <60s recovery-after-internet-loss acceptance test is entirely about Conclave reconnect + REST re-sync, not any local fallback). Also note Wi-Fi bulbs themselves hold their own cloud connection ('direct' status field in Conclave status_change events distinguishes direct-to-cloud vs via-hub devices). Plan-B Art-Net remains the only sub-second-guaranteed path.
  - src: https://github.com/go-go-golems/go-go-parc/blob/main/Projects/2026/09/05/PROJ%20-%20Hubspace%20BLE%20-%20From%20Bluetooth%20Packets%20to%20Cloud%20Control.md and https://github.com/dresslerc/esphome-afero and https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md
- [HIGH] **The underlying Afero platform API (api2.afero.net /v1, documented in Afero's own devdocs and legacy SDK) offers a raw per-device write path the semantics layer wraps: POST /v1/accounts/{accountId}/devices/{deviceId}/actions {'type':'attribute_write','attrId':N,'data':'<hex little-endian>'} and POST .../devices/{deviceId}/requests with WriteRequest[]; official docs warn these are ASYNCHRONOUS — 'the API call may return before the actual read/write takes place' — so HTTP 2xx is not confirmation a bulb changed; confirmation must come from Conclave attr_change events.**
  - This asynchronous-ack semantics is the single most important fact for the acceptance targets: '95% of scene changes visibly start <2s' must be measured bulb-side (Conclave echo or camera), not by HTTP latency. The devices/{deviceId}/versions endpoint (used by aioafero every 6h) and GET /v1/accounts/{accountId}/devices?expansions=state%2Cattributes%2Ctimezone%2Ctags also exist on the platform host.
  - src: https://github.com/aferodeveloper/afero-devdocs/blob/main/docs/API-DeviceEndpoints.md and https://raw.githubusercontent.com/aferodeveloper/AferoJavaSDK/master/afero-sdk-client-retrofit2/src/main/java/io/afero/sdk/client/retrofit2/api/AferoClientAPI.java
- [HIGH] **Platform-risk context: 'Myko' (Ace Hardware), the other Afero-based consumer brand that aioafero used to support, was migrated OFF Afero onto Tuya ('Myko+') between 2025-12-10 and 2026-01-31, breaking all reverse-engineered integrations for those users; aioafero's current constants file now lists only the 'hubspace' client. Hubspace itself remains on Afero as of Sep 2026 and Home Depot keeps investing (Hubspace Connect switch-to-light direct pairing; the House Beautiful Whole Home program), but a partner-initiated backend migration is a demonstrated, not hypothetical, failure mode for cloud-API-dependent installs.**
  - jdeath issues #219 'Myko+ No Longer Supported' and #223 'Myko+ migration' document devices silently disappearing from the integration as accounts migrated. For a 6-week activation window the risk is negligible, but for pitching a bespoke long-lived replacement app to the client afterward, this is the headline dependency risk (no contract, no deprecation policy, endpoints can move from v1 to v2 silently — the app already uses /v2 semantics while the community is on /v1).
  - src: https://github.com/jdeath/Hubspace-Homeassistant/issues/219 and https://github.com/jdeath/Hubspace-Homeassistant/issues/223
- [MEDIUM] **A bespoke kiosk/operator app is highly feasible on the documented surface (Keycloak login, metadevices list, per-device state PUT, Conclave push), and aioafero even ships mitmproxy how-to docs (docs/mitm/: install.rst, daily_use.rst — filter hosts accounts.hubspaceconnect.com, api2.afero.net, semantics2.afero.net, package io.afero.partner.hubspace) that make the decisive group/scene capture a documented afternoon task rather than novel research; a recent independent Swift client (Michael-Place/menere HubspaceClient) confirms the auth+transport re-implements cleanly outside Python.**
  - Differentiation for the pitch: official app has no kiosk mode, no multi-account dashboard, no zone choreography; the API supports batched multi-attribute PUTs and push state, enough for a polished guest UX. Risks: ToS (no official public API; the reverse-engineered ecosystem persists openly since 2021 without documented C&D, but a commercial pitch to Home Depot's own client should seek Afero/THD blessing), UA/403 filtering, unpublished rate limits, and silent v1→v2 migration.
  - src: https://github.com/Expl0dingBanana/aioafero/tree/main/docs/mitm and https://github.com/Michael-Place/menere

## Numbers
- Keycloak access token lifetime (hubspace_android) = **~118-120 seconds (aioafero hardcodes DEFAULT_TOKEN_TIMEOUT=118s, 2s expiry buffer) — design everything around refresh tokens** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py)
- State-write batching = **N attributes per bulb = 1 PUT; N bulbs = N PUTs (no public multi-device PUT on semantics2)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/controllers/base.py)
- Rule execution call count (platform primitive) = **1 POST ({'type':'execute_actions'}) triggers all deviceActions in a rule server-side** (https://raw.githubusercontent.com/aferodeveloper/AferoJavaSDK/master/afero-sdk-core/src/main/java/io/afero/sdk/client/afero/models/RuleExecuteBody.java)
- Conclave defaults = **conclave-stream.afero.io:443 (SDK default; live host assigned per conclaveAccess call, e.g. conclave-stream1.afero.net); read timeout 75s; heartbeat-idle multiplier 2.0; reconnect backoff 1s→60s doubling; invalid-token error code 906** (https://raw.githubusercontent.com/aferodeveloper/AferoJavaSDK/master/afero-sdk-core/src/main/java/io/afero/sdk/conclave/ConclaveClient.java and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/client.py)
- HA integration polling with push enabled = **REST true-up every 900s (15 min) default; Conclave carries realtime; pre-Conclave the integration polled every 30s** (https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md)
- 403 lockout heuristic = **3 consecutive 403s on a device's state GET → aioafero pauses polling that device until next discovery; MAX_RETRIES=3; version checks every 21600s** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py)
- BLE session crypto = **AES-128-GCM, 12-byte nonce, 6-byte truncated tag; envelope = u16le len + u32le seq + ct + tag[6]; session record = key[16]+IV[12]+counter[4]; GATT service 7a5a0068-6469-7545-4c42-6e6162696b** (https://github.com/go-go-golems/go-go-parc/blob/main/Projects/2026/09/05/PROJ%20-%20Hubspace%20BLE%20-%20From%20Bluetooth%20Packets%20to%20Cloud%20Control.md)
- aioafero current release = **9.3.0 (2026-09-15), Python >=3.12** (https://pypi.org/project/aioafero/)
- Afero module ↔ appliance MCU poll rate (fan teardown) = **1 status request per second over UART; module stops accepting app commands if MCU stops replying** (https://github.com/dresslerc/esphome-afero)
- Published rate limits = **NONE public — no documented req/s numbers anywhere; only the 403-filtering behavior above** (https://github.com/api-evangelist/afero (notes no machine-readable spec; api.afero.io/api-docs returns 401))

## Bench tests
- DECISIVE: mitmproxy the official Hubspace app (follow aioafero docs/mitm/install.rst + daily_use.rst; package io.afero.partner.hubspace; filter accounts.hubspaceconnect.com, api2.afero.net, semantics2.afero.net) while (a) toggling an app-created Group of 40+ bulbs and (b) creating+applying an app Scene — count HTTP calls: 1 call to a rules/scenes endpoint = server-side fan-out exists and the kiosk should use it; N metadevice PUTs = the app is no better than aioafero and the Python bridge's concurrency IS the architecture.
- Rules-engine probe with the kiosk's hubspace_android token: GET https://api2.afero.net/v1/accounts/{accountId}/rules?expansions=schedule (read-only, safe) — if scenes/automations built in the official app appear as Rule objects with deviceActions[], then POST /v1/accounts/{accountId}/rules/{ruleId}/actions {"type":"execute_actions"} on a 40-bulb test rule and measure first-to-last bulb spread vs test #3.
- Fan-out latency baseline: 40 bulbs on one account, fire 40 parallel PUTs /v1/accounts/{aid}/metadevices/{id}/state via asyncio.gather (each PUT batching power+color+brightness in one values[] list); film at 60fps and measure command-send→first-visible-change (target <2s p95) and first-to-last spread (target <2s); repeat 100x for the zero-wrong-bulb count; also compare /v2/ vs /v1/ state endpoint behavior.
- Conclave at scale: open one Conclave session for the 200-bulb canopy account (POST conclaveAccess {'user':true,'softHub':false}); apply scenes continuously for 8h; verify every PUT is echoed as attr_change within budget, log heartbeat gaps, ConclavePushStaleError occurrences, reconnect storms, and whether 200 devices on ONE account even receive complete event coverage (no public data exists at this device count — also confirm account device-count limits by onboarding all 200).
- Rate-limit ramp: from one IP/account, ramp semantics2 PUT rate (1→5→10→20→40 req/s) and log first 429/403 and Retry-After headers; separately verify the 3-consecutive-403 state-GET lockout and whether it is per-device, per-account, or per-IP — Home Depot's separate-accounts-per-vignette advice suggests per-account throttling; no public numbers exist.
- Token discipline under load: run refresh-token rotation every ~110s for 12h on 5 concurrent accounts (kiosk + 4 iPads) from one venue IP; confirm Keycloak doesn't rotate/invalidate refresh tokens or fingerprint the aioafero UA; capture the exact expires_in Keycloak actually returns.
- Recovery drill: kill venue WAN for 5 min mid-show, restore, and time (a) Conclave reconnect (expect 1-60s backoff), (b) REST reconciliation completing, (c) first successful scene apply — validates the <60s recovery target and whether bulbs themselves rejoin cloud fast or need power-cycle.
- Provisioning throughput: time BLE onboarding per A19 bulb via the app on the final install SSID (bulbs must be provisioned on the exact SSID/password used at the venue — test that a pre-staged bulb moved to a different SSID requires full re-onboarding), measure failures/retries per 50 bulbs, and test whether 5 phones onboarding in parallel on 5 accounts interfere in a dense 2.4GHz environment.

## Open questions
- Does the official app send ONE call for a group/scene apply or N per-device calls? (No public capture exists; AferoClientSceneMixin proves a scene API entity, the legacy rules engine proves a one-call primitive, but the wire truth needs the mitm capture.)
- What endpoints does AferoClientSceneMixin call — legacy /v1/accounts/{aid}/rules on api2.afero.net, or a newer /v2 semantics scenes resource on semantics2.afero.net — and does the hubspace_android Keycloak token authorize rule create/execute?
- Are there per-account device-count or event-throughput ceilings that make 200 bulbs on one account (or one Conclave channel) infeasible, forcing the 5-zone/5-account split?
- What are the actual rate limits (req/s, burst, per-IP vs per-account) on semantics2 PUTs and the Keycloak token endpoint?
- Is the /v1/ semantics surface on a deprecation path given the app already uses /v2/ (and would a mid-October server change strand the aioafero-based bridge)?
- Can a 'user'-type Conclave session WRITE attributes via say/whisper frames (the SDK exposes write primitives historically used by hubs), which would be a lower-latency command path than REST?
- Does Afero/THD tolerate or object to a commercial bespoke client (no ToS/API license exists publicly; ecosystem unchallenged since 2021, but the House Beautiful context likely warrants asking Afero directly — Afero is the actual platform vendor behind the partner app)?
- Do ~200 always-on RGB A19s on 2.4GHz maintain stable cloud connections through the venue's wired-AP mesh under show-floor RF congestion (the 'direct' Conclave status flag will show per-bulb connectivity)?
