# afero-platform

**HEADLINE:** Afero's Hubspace cloud is fully mapped and controllable via the aioafero stack (api2.afero.net REST + Conclave TLS push gives you sub-2s state feedback), but there is NO sanctioned API program, the developer portal is dead, Afero is unreachable even to community maintainers, and no credible Matter support exists for Hubspace as of Sep 2026 — so the activation rides an unsanctioned-but-technically-solid cloud path with aggressive rate limits as the #1 bench risk.

## Findings
- [HIGH] **Afero is the enterprise IoT PaaS behind Hubspace, and Hubspace is literally an Afero partner app — the Android package ID is io.afero.partner.hubspace**
  - Afero (Los Altos, founded 2014 by Joe Britt and Shin Matsumura) runs a partner-tenant model: Home Depot's Hubspace and Kingfisher's Myko (Europe) are white-label deployments of the same platform. Home Depot Ventures is an investor, and the Jan 7 2026 CES 'Whole Home' announcement names Afero as the 'enterprise IoT platform and security backbone,' with TI chips and a Kwikset lock powered by Hubspace coming later in 2026. Platform claims: millions of devices, 200+ product categories, 50+ manufacturers.
  - src: https://play.google.com/store/apps/details?id=io.afero.partner.hubspace and https://corporate.homedepot.com/news/products/whole-home-integration-powered-hubspace and https://www.afero.io/html/home/case-study-home-depot.html
- [HIGH] **The Hubspace cloud surface is: api2.afero.net (REST), semantics2.afero.net (data virtual-host), accounts.hubspaceconnect.com (Keycloak, realm 'thd'), with metadevice endpoints**
  - From aioafero v1_const.py: API_HOST=api2.afero.net, API_DATA_HOST=semantics2.afero.net (sent as an HTTP Host header override on discovery/state GETs while the TLS connection goes to api2.afero.net), AUTH_OPENID_HOST=accounts.hubspaceconnect.com, AUTH_REALM=thd, client_id=hubspace_android, redirect=hubspace-app://loginredirect. Endpoints: GET /v1/users/me (account id), GET /v1/accounts/{id}/metadevices?expansions=state,capabilities,semantics (discovery), GET/PUT /v1/accounts/{id}/metadevices/{id}/state (state read/write as functionClass/functionInstance/value JSON), GET /v1/accounts/{id}/devices/{id}/versions (firmware).
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py
- [HIGH] **Auth is Keycloak OAuth2 authorization-code + PKCE with HTML form scraping, ~2-minute access tokens, long-lived offline_access refresh tokens, and a possible OTP challenge that can break unattended kiosk logins**
  - aioafero performs GET /auth/realms/thd/protocol/openid-connect/auth (PKCE challenge, scope 'openid offline_access'), scrapes the Keycloak login form (session_code/execution/tab_id), POSTs credentials to /login-actions/authenticate, then exchanges the code at /protocol/openid-connect/token; refresh uses scope 'openid email offline_access profile'. If Keycloak returns a kc-otp-login-form the library raises OTPRequired — fresh accounts logging in from a new IP may hit this, so pre-mint and persist refresh tokens before install week. Library defaults assume 118s access-token life; the Emkraan HA integration states 'Access tokens expire after 118 seconds' and refreshes proactively.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py and https://github.com/Emkraan/homeassistant-hubspace
- [HIGH] **Conclave is Afero's realtime push service: a raw TLS socket (not WebSocket) with newline-delimited JSON frames, minted via POST /v1/accounts/{accountId}/conclaveAccess — and aioafero 9.x fully implements it**
  - The conclaveAccess response supplies host (e.g. conclave-stream1.afero.net), port, ssl, zlib compression flag, a short-lived SINGLE-USE socket token (not the OAuth JWT — using the JWT was the historic 'hello works, login rejected' bug) and channelId (the account UUID). Protocol: server hello/tunnel → client login frame {channelId, accessToken, type, version, protocol:2} → welcome; heartbeats are bare newline acks at a server-advertised interval (default 60s). Push events: private/attr_change (attribute id+value, mapped to functionClass via device semantics), private/status_change (available/visible/direct), public/invalidate kind=add|remove target=metadevices|devices for inventory changes. Mint a fresh token on every reconnect. This is how the kiosk bridge gets <2s confirmation that bulbs actually changed without hammering polls.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/access.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/protocol.py
- [HIGH] **The historical developer Cloud API (api.afero.io) is documented and shows the partner-centric design: password-grant OAuth with per-partner Basic credentials, async attribute actions, and a full partner OTA pipeline**
  - POST /oauth/token (HTTP Basic = base64(clientId:clientSecret), grant_type=password, token ~4h, example expires_in=16086, scope 'partner account'); GET /v1/users/me returns account + partner privileges; POST /v1/accounts/{accountId}/devices/{deviceId}/actions submits attribute reads/writes with hex little-endian data and is explicitly ASYNCHRONOUS ('if the device is offline the request may never complete'); OTA endpoints live under /v1/ota/partners/{partnerId}/... (firmware types, pool, binaries, moveToRepository, deviceType associations, per-image push, tags). OAuth client credentials were 'issued to a partner and viewed in the Afero Profile Editor under VIEW > ACCOUNT INFO' with an explicit warning that developer credentials must not be used in production. Note this is the legacy developer surface — Hubspace consumer accounts live on api2.afero.net with the metadevice layer instead.
  - src: https://raw.githubusercontent.com/api-evangelist/afero/main/openapi/_original/afero-cloud-api-openapi.yml and https://raw.githubusercontent.com/api-evangelist/afero/main/authentication/afero-authentication.yml
- [HIGH] **CRITICAL — there is NO sanctioned/commercial API access path usable for this activation: the developer portal is shut down, no partner program is publicly offered, and Afero does not answer integration inquiries**
  - developer.afero.io 301-redirects to afero.io and all doc subpaths (CloudAPIs, Projects, Hardware, API-OAuthEndpoints etc.) return 404; the ReadTheDocs mirror (afero-docs.readthedocs.io) is partial and omits all Cloud API pages; console.afero.io is still live but only for existing partner accounts with no signup. The aioafero maintainer Christopher Dohmen wrote on Oct 3 2025: 'I have been unable to get in contact with Afero regarding a local integration' — no Afero or Home Depot response exists anywhere in the HA community thread. The only enterprise path is a business-development conversation (afero.io contact, 650-899-0091) or via the client's own Home Depot relationship — neither is a productized API nor achievable before Oct 20. Consequence: the kiosk bridge necessarily impersonates the Android app OAuth client (hubspace_android) on consumer accounts — technically stable (two active HA integrations do this at scale) but unsanctioned, so keep the client informed and hold Plan B (Art-Net/DMX) ready.
  - src: https://community.home-assistant.io/t/hubspace-formal-integration-through-ha/702572 and https://console.afero.io/ and https://afero.io/
- [MEDIUM] **No credible Matter support exists for Hubspace as of Sep 19 2026 — Matter unlocks nothing for this activation and local control remains impossible on Hubspace bulbs**
  - HowToGeek (Mar 2024) states Hubspace has no native HomeKit or Matter support; the CES 2025 product reveals and the Jan 7 2026 CES 'Whole Home' / Hubspace 2.0 announcements (Hubspace Connect switch-to-light binding, Circadian Lighting, Kwikset, TI) contain zero Matter mentions; CSA certification database keyword probes for 'hubspace' and 'afero' returned no entries; the only 'Matter-enabled Hubspace' claims come from SEO-farm review sites (smarthomiehub.com, roipad.com) with no sourcing. Hubspace 2.0's 'Hubspace Connect' is a proprietary device-to-device binding for switches/dimmers controlling lights off-circuit — not Matter, not an open local API, and not applicable to a Python bridge. Plan on cloud-only control for the ~200 A19 bulbs.
  - src: https://www.howtogeek.com/home-depots-hubspace-still-needs-work-to-compete-in-smart-home/ and https://corporate.homedepot.com/news/products/whole-home-integration-powered-hubspace and https://www.gearbrain.com/hubspace-2-0-smart-home-platform-guide-2674403833.html
- [HIGH] **Afero rate-limits aggressively and publishes no quotas; community integrations floor per-device state polling at 2 seconds — write fan-out for 200 bulbs is the single biggest unquantified risk**
  - The Emkraan HA integration README states 'Floored at 2s - Afero rate-limits aggressively' (default per-device delta poll 30s, discovery 3600s, stale-data grace 10min); jdeath/Hubspace-Homeassistant defaults to 900s REST polling with Conclave push default-on precisely to avoid REST pressure. aioafero hard-codes MAX_RETRIES=3 and pauses per-device polling after 3 consecutive 403s on state GETs (STATE_FETCH_FORBIDDEN_LIMIT), implying Afero serves 403s (not only 429s) under pressure. No public documentation of per-account/per-IP quotas exists anywhere — the Sep 23 bench gate must empirically find the 429/403 onset for burst PUTs to /metadevices/{id}/state. Official Afero attribute guidance ('no more than one write/update per second' per device) suggests server-side expectations are modest.
  - src: https://github.com/Emkraan/homeassistant-hubspace and https://github.com/jdeath/Hubspace-Homeassistant and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py and https://afero-docs.readthedocs.io/en/latest/AttrModel/
- [HIGH] **The Afero attribute model layers Hubspace 'metadevices' (semantic functionClass/functionInstance states) over raw numbered attributes, and writes are eventually-consistent by design**
  - Core platform: devices expose typed attributes (MCU attributes numbered 1-1023; Boolean/SINT8/string types; one value per attribute), and official docs warn 'writing to ASR does not mean the attribute has been synchronized with the Cloud; synchronization may take some time.' The Hubspace layer translates raw attribute IDs to semantic states via per-device 'semantics' delivered in the discovery expansion — aioafero's conclave/semantics.py resolves Conclave attribute-id pushes back to functionClass/functionInstance (e.g. color-rgb, brightness, power). Practical effect: scene writes are async at two levels (REST accept ≠ device applied), so the Conclave attr_change stream is the only trustworthy 'bulb actually changed' signal for the acceptance metrics.
  - src: https://afero-docs.readthedocs.io/en/latest/AttrModel/ and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/events.py
- [HIGH] **OTA is entirely partner-controlled (Home Depot/Afero can push firmware to the fleet), which is an event-week risk you can monitor but not block**
  - The OTA pipeline (/v1/ota/partners/{partnerId}/... with per-deviceType firmware image associations and push) belongs to the partner realm — consumer accounts cannot schedule or veto updates. aioafero polls GET /v1/accounts/{id}/devices/{id}/versions every 6 hours to surface firmware versions. Mitigation for Oct 20-29: record all bulb firmware versions at install, re-check daily during the soak, and avoid tapping any update prompts in the Hubspace app; a mid-event fleet OTA wave would be visible as version changes plus temporary device unavailability.
  - src: https://raw.githubusercontent.com/api-evangelist/afero/main/openapi/_original/afero-cloud-api-openapi.yml and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py
- [HIGH] **The current library lineage is hubspace_async → aiohubspace (ended at 1.2.0) → aioafero, now at 9.3.0 released Sep 15 2026, actively maintained, MIT, Python >=3.12**
  - aioafero (Chris Dohmen / Expl0dingBanana, MIT) is the canonical community client: typed controllers (light, lock, switch, fan, valve, thermostat, security system...) on AferoBridgeV1, Conclave push with REST fallback, split-device handling, and docs at aioafero.readthedocs.io. Two HA integrations consume it: jdeath/Hubspace-Homeassistant (381 stars, uses PyPI aioafero, Conclave default-on, 900s fallback poll) and Emkraan/homeassistant-hubspace (vendors a patched copy, 30s delta poll, per-device availability tracking, anti-cascade design). For the kiosk bridge, pin aioafero==9.3.0 and mirror Emkraan's proactive token refresh + per-device availability patterns.
  - src: https://pypi.org/project/aioafero/ and https://pypi.org/pypi/aiohubspace/json and https://github.com/jdeath/Hubspace-Homeassistant and https://github.com/Emkraan/homeassistant-hubspace
- [HIGH] **No public Afero status page exists, so the activation needs its own health monitoring of the cloud dependency**
  - status.afero.io does not resolve and afero.statuspage.io redirects to statuspage.io's homepage (no tenant). The Afero Console shows platform status to partners only. The bridge should therefore self-monitor: Conclave socket liveness (heartbeat interval ~60s), REST error rates, and a canary bulb per zone, with the <60s recovery target validated against deliberate WAN cuts rather than any vendor SLA.
  - src: https://afero.statuspage.io/ and https://console.afero.io/

## Bench tests
- Rate-limit onset mapping (gates everything): on one Hubspace account with 40 real bulbs, issue PUT /v1/accounts/{id}/metadevices/{id}/state bursts at concurrency 5/10/20/40, then sustain 100 scene changes; log first HTTP 429/403, any Retry-After headers, and whether limits are per-account, per-IP, or per-token by repeating from a second account on the same IP and the same account on a second IP.
- Scene latency distribution: wire Apply→Conclave attr_change→camera-visible light change timing for a 40-bulb zone write; measure P50/P95 apply-start latency, first-to-last-bulb spread, and full-scene-correct time against the <2s/<5s/<10s targets, using the Conclave stream (not REST polls) as the applied-state oracle.
- Server-side group fan-out probe: create a Hubspace app room/group containing 40 bulbs, discover whether the group appears as its own metadevice, and test whether one state PUT to the group metadevice changes all members (this would cut scene writes from 200 to 5 and likely dodge rate limits entirely).
- Fresh-account login + OTP behavior: create the 5+ vignette accounts, log in via aioafero from the actual venue network hardware; record whether Keycloak serves kc-otp-login-form (OTPRequired), where the OTP is delivered, and confirm cached refresh tokens survive 8h+ soak and a 24h gap without interactive re-login.
- Conclave resilience: verify conclaveAccess tokens are single-use on reconnect (mint fresh each time), run 5 concurrent Conclave sockets (one per account) from one IP for 8 hours checking for server-side disconnects, then cut WAN for 60s and 10min and measure reconnect + full state reconciliation time against the <60s recovery target.
- OTA freeze check: record every bulb's firmware via GET /v1/accounts/{id}/devices/{id}/versions at bench start, monitor daily through the soak for unsolicited version changes or device-unavailable windows, and document bulb behavior (light output during update) if any OTA lands.

## Open questions
- What are the actual numeric rate limits (requests/min per account, per IP, per token) on api2.afero.net state writes, and does Afero throttle with 429+Retry-After or silent 403s? Nothing is published; only the bench can answer.
- Do Hubspace room/group metadevices accept a single state PUT that fans out server-side to member bulbs? If yes, the 200-bulb canopy becomes 5 writes per scene and the rate-limit risk mostly evaporates; neither aioafero docs nor HA integrations confirm this.
- Can the client's Home Depot relationship (this is a Home Depot-commissioned activation) unlock anything from Afero — even informal rate-limit whitelisting for 5 named accounts during Oct 20-29? Afero ignored the aioafero maintainer, but a THD-internal request is a different channel; needs a business-side ask this week given the Sep 23 gate.
- Will Keycloak at accounts.hubspaceconnect.com challenge new venue-IP logins with OTP (and is it email OTP or TOTP), and are there account-lockout thresholds that 5 accounts × repeated bench logins could trip?
- Is there any per-account device-count ceiling that ~200 bulbs on one canopy account would hit (Home Depot support anecdotes suggest large accounts degrade; separate accounts per vignette advice may exist partly for this)?
- Has any single 2026 Hubspace SKU quietly shipped Matter (check retail packaging in-store and the CSA database manually via its JS search) — and specifically the 12A19060WRGBWH A19 color bulbs planned for the canopy?
