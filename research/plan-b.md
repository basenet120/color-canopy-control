# plan-b

**HEADLINE:** A wired 12V WS2811 pixel canopy driven by xLights/xSchedule over sACN is the cheapest credible plan B (~$700-900 all-US-stock hardware, ~25ms scene latency vs the 2s target); if the canopy must remain literal A19 bulbs in E26 sockets, pre-flashed Athom WLED ESP32-C3 bulbs (~$14.63 ea, ~$3.1k for 210) drop into the same sockets and take local DDP/sACN — while flashing or locally controlling real Hubspace bulbs is a documented dead end (eFuse-locked Leedarson/ESP32 modules, cloud-only API, no Matter).

## Findings

  - These look like genuine C9 holiday bulbs (faceted cover over each node), on-theme for a late-October House Beautiful activation. 2-year warranty; vendor warns to test within 90 days and not cut strings. Cheaper raw option: HolidayCoro 100-count 12V WS2811 bullet strings $29.95/100 ($0.30/pt), in stock, ships in 24h, 0.55W/node — but bare bullets need covers (HolidayCoro's C7/C9 cover category currently lists 0 products; printable/AliExpress covers exist), so PixaBulbs are the turnkey pick.

  - Any one of these drives all 200 canopy points on 1-4 ports with one $19-37 Mean Well LRS-350-12 350W PSU (200 px x 0.55W = 110W max). Advatek PixLite A4-S Mk3 (~EUR585, 1020 px/output, 24 universes Art-Net/sACN) is the pro-grade equivalent if the fabricator wants a commercial brand. At 40fps the frame period is 25ms, so a scene change visibly starts within ~1 frame + LAN transit — roughly 25-50ms, about 40-80x inside the 2s acceptance target, with first-to-last-bulb spread of one frame (all pixels update in the same frame).

- [HIGH] **Kiosk integration for plan B is a documented one-line HTTP call: xSchedule (xLights' player) exposes REST endpoints like /xScheduleCommand?Command=PressButton&Parameters=<label> and 'Play specified playlist <name>', plus /xScheduleQuery?Query=GetPlayingStatus and a WebSocket JSON interface with optional password**
  - The existing Python kiosk bridge keeps aioafero for the 4 Hubspace vignettes and adds either (a) direct sACN/DDP sending via a Python library, or (b) HTTP calls to xSchedule playing pre-built xLights scene sequences. Scene = playlist; Apply = one GET request; status polling built in. FPP (on Kulp/Pi) offers an equivalent REST API. Zero license cost — xLights/xSchedule/FPP are free open source.
  - src: https://github.com/xLightsSequencer/xLights/blob/master/documentation/xSchedule%20API%20Documentation.txt
- [HIGH] **For a literal A19-in-socket look, Athom sells pre-flashed WLED bulbs: 12W E26/E27 color bulb on ESP32-C3 with addressable LEDs, $14.63 on sale ($19.50 list), in stock; 15W variant listed but out of stock; BR30 RGBCW $13.98 — 210 bulbs (incl. 10 spares) ≈ $3,072 and they screw into the exact same 200-socket E26 canopy grid planned for Hubspace bulbs**
  - This is the like-for-like swap: identical household-bulb silhouette, same mains socket infrastructure, but locally controllable. WLED accepts E1.31/sACN, Art-Net, and DDP; docs state 170 LEDs/universe, up to 9 universes, and recommend <=510 LEDs per node for 'a fluent 25ms (40fps) or more framerate' — a whole-bulb node is trivial (a handful of LEDs). Caveats: 200 Wi-Fi clients needs 4-6 dedicated APs with unicast DDP at 10-20fps and WLED 'WiFi sleep' disabled (docs note sleep causes stutter); Athom ships from China (order by ~Sep 26 to leave buffer before Oct 20 install); WLED sync groups give a degraded-mode fallback if the sender dies.
  - src: https://www.athom.tech/wled and https://kno.wled.ge/interfaces/e1.31-dmx/ and https://kno.wled.ge/interfaces/udp-realtime/

Both accept Art-Net so latency profile matches the pixel plan.

- [HIGH] **Flashing real Hubspace bulbs with Tasmota/ESPHome/WLED is a proven dead end: the Home Assistant community spent 2021-2023 on a Hubspace RGBWW downlight (SKU 1005731250) containing a Leedarson/Afero LA02301 ESP32 module and found 'the bootloader has Download Mode disabled' via burned eFuses — every flash attempt failed; the only success was physically transplanting an M5Stack Stamp ESP32 and hand-wiring five GPIOs to the LED channels**
  - A 200-bulb transplant is obviously not viable in 4 weeks. Current-generation Hubspace A19s are also Leedarson-built (Leedarson America is the FCC responsible party, grantee 2AB2Q; one A19 model 12CFA1960WCCT01 = FCC ID 2AB2Q-A800SG-G1Z) and Leedarson's current universal Wi-Fi/BLE module LA66701 is an ESP32-C3 SiP with embedded 4MB flash — same vendor, same lock-down posture expected (ESP32-C3 supports Secure Boot V2/flash encryption and Afero's whole platform pitch is hardware security). Treat custom firmware on Hubspace hardware as OFF the table for this show.
  - src: https://community.home-assistant.io/t/help-trying-to-flash-esp32-in-home-depot-bulb/326294 and https://device.report/manual/9346936 and https://device.report/manual/3550044
- [HIGH] **There is no local-network API for Hubspace and no usable BLE control path for lights: every community integration (jdeath/Hubspace-Homeassistant + aioafero, homebridge-hubspace, hubspace-ng) talks to the Afero cloud; the only BLE work (jdeath/hubspace_ble) targets Defiant locks, is explicitly 'a future Home Assistant Integration', and its test script 'only extracts the device ID and some other unknown data at this time'**
  - The 'HubSpaceLocal' repo that sounds promising (DaedalusStudios/HubSpaceLocal, 'direct connection') is just a fork of Home Assistant core with no evident working local protocol — not a real path. Additionally the LA66701 module manual states Wi-Fi and BLE 'cannot transmit simultaneously', which explains why a bulb already joined to Wi-Fi is not a reliable BLE control target even in principle. Conclusion: actual Hubspace bulbs can only be driven through the Afero cloud (aioafero), so plan B must swap hardware, not protocols.
  - src: https://github.com/jdeath/hubspace_ble ; https://github.com/jdeath/Hubspace-Homeassistant ; https://github.com/DaedalusStudios/HubSpaceLocal ; https://device.report/manual/9346936
- [MEDIUM] **No Hubspace A19 has Matter support and none is announced for late 2026: HowToGeek (Mar 2024) reported no native Matter or HomeKit; the Dec 16 2025 GearBrain 'Hubspace 2.0' deep-dive lists only Alexa and Google Assistant as ecosystem layers with no Matter/HomeKit/local-control mention; Home Depot's own Jan 7 2026 'Whole Home Integration Powered by Hubspace' corporate post touts Hubspace 2.0 Connect, 200+ products, Kwikset locks (2026) and Texas Instruments chips — and never says the word Matter**
  - So a 'wait for Matter and control the same bulbs locally' plan B does not exist for this October. (Some SEO-grade sites like smarthomiehub.com claim 'Matter-enabled Hubspace products integrate with Apple Home' but this contradicts every primary/dated source and should be disregarded.) Even if a Matter bulb SKU appeared, 200-node Matter-over-WiFi group scene latency would itself need a bench pass — moot for this timeline.
  - src: https://www.howtogeek.com/home-depots-hubspace-still-needs-work-to-compete-in-smart-home/ ; https://www.gearbrain.com/hubspace-2-0-smart-home-platform-guide-2674403833.html ; https://corporate.homedepot.com/news/products/whole-home-integration-powered-hubspace
- [MEDIUM] **The hybrid pattern used in real retail is 'real product where hands touch it, dedicated show control where the spectacle is': Philips Hue's Best Buy endcap was a purpose-built 8-ft interactive fixture by display fabricator LG&P demonstrating dimming/brightening/color on a controlled rig, and brand-activation pixel work is normally driven by show-control tools like ENTTEC ELM outputting DMX/Art-Net/sACN/KiNET live or on a timeline — not by the consumer cloud app path**
  - Recommended hybrid for Charleston: keep genuine Hubspace hardware in the 4 staff-paced vignettes (low device count, staff can pace the demo, cloud latency tolerable) plus a touchable 'hero shelf' of real EcoSmart A19s at eye level near the kiosk; run the 200-point canopy on pixels/WLED via sACN where latency and zero-wrong-bulb targets actually bite. Latency-hiding UX if any cloud path stays guest-facing: optimistic UI — reflect the chosen mood on the kiosk screen within 100ms (humans notice delay at ~100ms), play a branded 'mixing your color' preview animation sized to cover worst-case cloud propagation, and stage the physical reveal (e.g., zone-by-zone sweep) so the first visible change is a pre-armed fast command and stragglers land inside the choreography; roll back UI on failure.
  - src: https://www.lginstore.com/projects/philips-hue ; https://www.enttec.com/ ; https://simonhearne.com/2021/optimistic-ui-patterns/
- [HIGH] **RECOMMENDATION — cheapest credible plan B, orderable this week, install-ready by mid-Oct: 'C9 pixel canopy' ≈ $700-900: 5x Gilbert C9 PixaBulb 50-node strings $194 (200 pts + 50 spares), Falcon F16v5 $265 (plus a $24-35 ESPixelStick/Athom-Ethernet cold spare), 2x Mean Well LRS-350-12 ~$75, xConnect extensions/tees/fusing/mounting ~$150; xLights/xSchedule free; kiosk fires xSchedule REST or raw sACN from Python**

## Bench tests
- Latency proof: wire 50 PixaBulb/WS2811 pixels to an F16v5 (or ESPixelStick), trigger a scene from the kiosk Python bridge via xSchedule REST (/xScheduleCommand?Command=PressButton&Parameters=Scene1) and via raw sACN from the python 'sacn' library; film kiosk screen + pixels at 240fps and measure Apply-to-first-light (accept if <100ms) and first-to-last-pixel spread (expect <=1 frame / 25ms).
- Soak: run xSchedule looping 40fps sequences on 200 pixels for 8h; log controller frame drops (FPP/Falcon status page), PSU and controller temperature at the 4h/8h marks, and run a scripted 100-scene-change pass photographing the grid after each change to prove zero wrong/missed bulbs.
- Athom WLED A19 passability + Wi-Fi density: order 10-20 bulbs NOW (China lead time); (a) side-by-side lit comparison against an EcoSmart Hubspace A19 behind the canopy diffusion — does it read as the same household bulb to a guest at 8ft? (b) join all bulbs to one dedicated 2.4GHz AP, drive with unicast DDP at 10 and 20fps, measure apply-to-light latency and packet loss over 2h, then extrapolate AP count for 200 nodes (target <=50 clients/AP); (c) disable WiFi sleep per WLED docs and re-measure; (d) kill the DDP sender and verify WLED preset/sync-group fallback keeps a static scene.
- Offline/recovery: with plan-B rig on an isolated show LAN (no internet), verify scenes still trigger (should be identical — no cloud dependency); cut mains to controller+PSU mid-scene, restore, and time to autoresume playlist (FPP/xSchedule autostart) — accept <60s.
- Rigging/electrical fit: confirm PixaBulb string weight and 6-inch spacing maps onto the 20x10 grid geometry (10x20ft = 24-inch pitch, so pixels need re-spacing into sockets/clips or a 2-ft-pitch custom-spaced order — Gilbert/HolidayCoro sell custom spacing); for the Athom path confirm 200 E26 socket circuit load with bulbs capped at a preset brightness (200x12W worst case = 2.4kW; measure real draw at show brightness).
- Only if a stakeholder still wants Hubspace flashing: sacrifice one 2026-production EcoSmart RGB A19, expose the Leedarson module UART, run esptool/espefuse read — expect UART download mode disabled/secure-boot eFuses burned, closing the question with evidence.
