# performance

**HEADLINE:** The Hubspace control path is cloud-only REST on Google Cloud with per-account quotas, an undocumented rate limit (community floor: 2s polling), a default of only 3 concurrent connections per host in aioafero, and a new subscribe-only Conclave push channel — meaning 200-bulb scene fan-out speed is entirely unproven publicly and must be bench-measured, while state feedback is now near-real-time.

## Findings
- [HIGH] **Commands cannot be batched or pushed: the June-2026 Conclave push channel is subscribe-only, so every bulb state change is an individual REST call**
  - aioafero's official docs state verbatim: 'Conclave is subscribe-only. Writes still go through controller methods / bridge.send_service_request (REST).' Conclave (added in aioafero PR #77, merged 2026-06-08) is a raw TLS socket (not websocket) to conclave-stream1.afero.net:443 delivering attr_change/status_change/invalidate events that patch the same cached device models REST polling uses. For the Color Canopy this means a 5-zone scene change = up to 200 individual PUTs to /v1/accounts/{id}/metadevices/{deviceId}/state; Conclave only gives you fast per-bulb confirmation feedback for the kiosk UI, not fast application.
  - src: https://aioafero.readthedocs.io/en/latest/user/conclave.html
- [HIGH] **Afero rate-limits aggressively but no public numeric threshold exists anywhere; the only observed bounds are a 2s polling floor and degradation seen at 10s polling**
  - The Emkraan/homeassistant-hubspace README (from-scratch 2026 integration) says: 'State polling interval | 30s | ... Floored at 2s - Afero rate-limits aggressively.' aioafero's official troubleshooting doc: 'The API rate-limits requests. Concurrent clients (phone app, Home Assistant, scripts) compete for the same quota. Reduce polling frequency with polling_interval or limit concurrent integrations.' Real-world: HA user llealloo (2025-07-18) changed polling 30s->10s and subsequently lost device names in API responses ('so maybe I got API rate limited?'); aioafero maintainer Expl0dingBanana replied (2025-07-20) 'It could be due to rate limiting.' Notably rate limiting manifested as degraded/partial responses, not clean 429s. No GitHub issue in jdeath/Hubspace-Homeassistant, aioafero, or Emkraan repos documents an actual 429 threshold, requests/min number, or IP ban.
  - src: https://github.com/Emkraan/homeassistant-hubspace and https://aioafero.readthedocs.io/en/latest/user/troubleshooting.html and https://community.home-assistant.io/t/add-support-for-hubspace-by-afero/306645/321
- [HIGH] **aioafero handles 429/503/504 as silently retryable with tiny linear backoff and caps concurrency at 3 connections per host — a built-in throughput ceiling you must patch for 200 bulbs**
  - In src/aioafero/v1/__init__.py: 'if resp.status in [429, 503, 504]: continue' inside 'while retries < v1_const.MAX_RETRIES' (MAX_RETRIES=3) with retry_wait = 0.25 * retries (0.25s/0.5s/0.75s); 403s are tracked separately and after STATE_FETCH_FORBIDDEN_LIMIT=3 consecutive 403s a device's state polling is paused until rediscovery. The aiohttp session is created with TCPConnector(limit_per_host=3). At 3 concurrent in-flight requests, 200 PUTs at an optimistic ~200-300ms RTT each ≈ 13-20s first-to-last spread — would fail the <2s spread target. The kiosk bridge must raise limit_per_host and/or split accounts; whether Afero's server side tolerates that is the key bench unknown.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py
- [MEDIUM] **Observed single-command latency on the cloud path is roughly 1-2 seconds app-to-bulb when healthy; 'almost instant' state feedback is reported with current integrations**
  - GitHub issue #34 (jdeath repo, 2023-04-14): 'The delay on sending the request is 1 to 2 sec and that is fine but if I want to do automation...it is taking 120 sec to run' (the 120s was the old poll-based architecture, since fixed). Hubspace support in Home Depot product Q&A: on Wi-Fi control 'should be pretty much instantly responsive,' on Bluetooth 'a couple of seconds.' HA user OvalZyre (2025-01-30): devices 'have been stellar for months - showing status almost instantly in HASS.' Worst path: Reviewed.com's review measured Alexa voice->Hubspace at 15-20s ('Alexa pauses to think about what I'm asking for 15 to 20 seconds') — avoid third-party voice chains at the activation. No one has published p95 command RTT measurements; the <2s visible-start target is plausible but unproven at fan-out scale.
  - src: https://github.com/jdeath/Hubspace-Homeassistant/issues/34 and https://www.homedepot.com/p/questions/EcoSmart-60-Watt-Equivalent-Smart-A19-Color-Changing-CEC-LED-Light-Bulb-with-Voice-Control-1-Bulb-Powered-by-Hubspace-12A19060WRGBWH1/322660146/5 and https://www.reviewed.com/smarthome/features/home-depot-hubspace-review
- [HIGH] **Access tokens live only 118 seconds; aioafero refreshes proactively with a 2s buffer — expect a token refresh roughly every 2 minutes per account, times 5-9 accounts**
  - aioafero auth.py: DEFAULT_TOKEN_TIMEOUT = 118, TOKEN_EXPIRY_BUFFER = 2, expiration = timestamp + expires_in - buffer. Auth is OAuth2 code+PKCE against Keycloak at accounts.hubspaceconnect.com. Conclave access tokens are separate, short-lived and effectively single-use: docs say always mint a fresh one via POST /v1/accounts/{accountId}/conclaveAccess on every reconnect and do not trust expires_timestamp. This is background load to account for in the soak test but not a latency problem per se.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py and https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/access.py
- [MEDIUM] **Multiple accounts in parallel has a documented rationale (quota is per-account/shared across clients) but zero public proof as a throughput multiplier; per-IP throttling is unknown**
  - aioafero's troubleshooting doc says concurrent clients 'compete for the same quota,' implying quota is keyed to the account — so 5 zone-accounts should have 5 independent quotas, matching Home Depot's own advice of separate accounts per vignette. Hubspace's account model supports this cleanly: devices live in 'Homes' under one account and 'You cannot share devices among Homes'; sharing = sharing credentials. But no GitHub issue, forum post, or doc demonstrates aggregate throughput scaling with account count, and nothing public says whether Afero also throttles per source IP (all kiosk accounts would share one NAT IP at the venue). No public IP-ban reports found at all.
  - src: https://aioafero.readthedocs.io/en/latest/user/troubleshooting.html and https://www.homedepot.com/c/ab/hubspace-faq/9ba683603be9fa5395fab9014e4790c0
- [HIGH] **Conclave push mechanics: ~60s server heartbeats, ~120s staleness detection, 60s login deadline, 1s->60s exponential reconnect backoff — no published push latency figures**
  - From aioafero conclave/client.py and docs: server advertises heartbeat in hello/welcome ('typically ~60 seconds', sent as bare \n); DEFAULT_READ_TIMEOUT=75.0s with wire-idle multiplier 2.0 (~120s staleness); DEFAULT_INITIAL_BACKOFF=1.0s doubling to DEFAULT_MAX_BACKOFF=60.0s; login must complete within 60s or 'push updates may be delayed'; READ_CHUNK_SIZE=65536; optional zlib compression; optional push_idle_timeout catches zombie sessions (ConclavePushStaleError). Events (attr_change/status_change) flow straight into device cache with no debounce/coalescing constants. Nobody has published tap-to-push-event latency; jdeath README calls it 'near real-time device changes'. For recovery: fresh conclaveAccess token per reconnect + max 60s backoff means the <60s internet-recovery target is architecturally reachable but needs verification.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/conclave/client.py and https://aioafero.readthedocs.io/en/latest/user/conclave.html
- [HIGH] **REST polling is heavyweight: 14 lights polled at 5s consumed ~1.5 GB/day (~87 KB per poll cycle); 200 bulbs would multiply this — size the venue uplink and prefer Conclave**
  - GitHub issue #216 (jdeath repo, 2025-12-30): 'my Hubspace integration has been using gigabytes of data per day. I dropped my polling rate from 5 to 30 seconds and it reduced it by a factor of 5' — ~1.5GB/day with 14 lights, measured over 30 minutes via HA System Monitor. Scaling naively, 200 bulbs at 30s polling could be on the order of 4+ GB/day of API traffic; Conclave push plus a slow REST true-up (jdeath v8 default: 900s) is the current-generation answer. jdeath v8.3.0 enables Conclave by default with 'REST polling remains as a true-up (default every 15 minutes / 900 seconds)'.
  - src: https://github.com/jdeath/Hubspace-Homeassistant/issues/216 and https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md
- [HIGH] **Afero cloud runs on Google Cloud (not AWS), has no public status page and no DownDetector/IsTheServiceDown coverage; outage signal exists only as anecdotes, including a >=43-minute 500-error event in July 2026**
  - DNS resolved today: api2.afero.net = 35.184.28.9 (PTR *.bc.googleusercontent.com), accounts.hubspaceconnect.com = same IP, semantics2.afero.net = 34.49.181.0 (GCP LB range), conclave-stream1.afero.net = 34.10.95.66 — all Google Cloud, so the famous 2025-10-20 AWS us-east-1 14h outage would not have hit Afero's API directly (it did kill Alexa/Ring paths; note your install week is that outage's anniversary, and GCP had its own major outage 2025-06-12). istheservicedown.com/problems/hubspace returns 404; no status.afero.io found. Documented incidents: GitHub issue #240 (2026-07-27) logged 500 Internal Server Error + connection timeouts to api2.afero.net for at least 43 minutes (10:07-10:50 AM); HA thread user jaaem (2025-01-31): 'Sometimes the API gets overloaded'; JustUseApp complaint tracker shows a constant stream (70 reports/24h; 27.0% connection issues, 19.8% not working, 11.7% login; complaints like 'app takes at least 5 minutes to load', 'all products are offline'). Plan for cloud loss with no vendor status page to point at.
  - src: DNS lookups (dig, 2026-09-19) plus https://github.com/jdeath/Hubspace-Homeassistant/issues/240 and https://justuseapp.com/en/app/1506042235/hubspace/problems and https://community.home-assistant.io/t/add-support-for-hubspace-by-afero/306645/321
- [HIGH] **Library/ecosystem status September 2026: aioafero 9.3.0 (released 4 days ago) is the current, very active library; the rename chain is hubspace_async -> aiohubspace (dead at 1.2.0, Apr 2025) -> aioafero; jdeath integration is at v8.3.0; a rival Emkraan integration focuses on exactly your failure modes**
  - PyPI: aioafero 9.3.0 (2026-09-15), 9.2.1 (09-13), 9.2.0 (09-12), 9.1.0 (09-03), 9.0.1 (08-09) — fast release cadence, Python >=3.12; aiohubspace last release 1.2.0 on 2025-04-07 ('updated from hubspace_async'). aioafero 8.0.0 (June 2026) decoupled auth from bridge; Conclave landed in the same window. Emkraan/homeassistant-hubspace is a separate from-scratch integration targeting 'devices that go unavailable and never recover' and 'commands that appear to work then silently revert' ('Historically the most common Hubspace complaint - a stale poll response overwriting an optimistic update'), with per-device availability, self-healing reload escalation, and a 10-min stale-data grace period to ride out 'brief Afero cloud blips' — its design choices are a checklist of the failure modes your kiosk bridge must handle.
  - src: https://pypi.org/pypi/aioafero/json and https://pypi.org/pypi/aiohubspace/json and https://github.com/Emkraan/homeassistant-hubspace
- [MEDIUM] **Historic maintainer verdict (older jdeath README, since removed): Hubspace updates are slow and the UI unresponsive, recommending other devices for HA integration**
  - Search-indexed text from the jdeath repo (older README revision, pre-v5; the sentence is absent from v5.10.0 and current v8.3.0 READMEs which only note 'Due to the cloud-first nature of Hubspace devices, an internet connection needs to be available, along with the Hubspace servers'): updates are slow, the UI can be unresponsive, devices are 100% cloud-reliant, and the developer 'would highly recommend finding another device.' The removal of this warning coincides with the aioafero rewrite + Conclave push era, suggesting the situation materially improved in 2025-2026 — but the underlying architecture (cloud round-trip per command) is unchanged.
  - src: https://github.com/jdeath/Hubspace-Homeassistant (older README revision, visible in search snippets; current README at https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md)
- [HIGH] **Cloud hosts and endpoints for the performance-critical path**
  - From aioafero v1_const.py and issue logs: API_HOST api2.afero.net (device commands: PUT /v1/accounts/{accountId}/metadevices/{deviceId}/state; same path GET for state), API_DATA_HOST semantics2.afero.net, auth accounts.hubspaceconnect.com (Keycloak), Conclave access minted at POST /v1/accounts/{accountId}/conclaveAccess returning host/port/ssl/compression/token/channel_id (host typically conclave-stream1.afero.net:443), Android UA template mimics the app (package io.afero.partner.hubspace). VERSION_POLL_INTERVAL_SECONDS = 21600 (6h). Discovery default 3600s; state polling default 30s in aioafero's bridge.
  - src: https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py and https://github.com/jdeath/Hubspace-Homeassistant/issues/69

## Numbers
- aioafero default state polling interval = **30 s (discovery 3600 s; version poll 21600 s)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py)
- Community-established polling floor (rate-limit driven) = **2 s ('Afero rate-limits aggressively')** (https://github.com/Emkraan/homeassistant-hubspace)
- Polling rate that triggered observed rate-limit degradation (lost device names) = **10 s (down from 30 s), July 2025** (https://community.home-assistant.io/t/add-support-for-hubspace-by-afero/306645/321)
- aioafero HTTP retry policy = **MAX_RETRIES=3; retryable statuses 429/503/504; backoff 0.25*retries (0.25/0.5/0.75 s); 3 consecutive 403s pause device polling** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/v1_const.py)
- aioafero HTTP concurrency cap = **TCPConnector(limit_per_host=3)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/__init__.py)
- Access token lifetime / refresh buffer = **118 s / 2 s buffer (proactive refresh)** (https://raw.githubusercontent.com/Expl0dingBanana/aioafero/main/src/aioafero/v1/auth.py)
- Single command send delay (user-reported, healthy cloud) = **1-2 s** (https://github.com/jdeath/Hubspace-Homeassistant/issues/34)
- Alexa voice -> Hubspace device worst-path delay = **15-20 s** (https://www.reviewed.com/smarthome/features/home-depot-hubspace-review)
- Conclave heartbeat / staleness / login timeout / reconnect backoff = **~60 s heartbeat; ~120 s staleness (2x heartbeat, read timeout default 75 s); login within 60 s; backoff 1 s doubling to 60 s max** (https://aioafero.readthedocs.io/en/latest/user/conclave.html)

- jdeath v8 integration defaults = **Conclave push ON by default; REST true-up every 900 s** (https://raw.githubusercontent.com/jdeath/Hubspace-Homeassistant/main/README.md)
- Documented Afero API incident (500s + timeouts to api2.afero.net) = **>=43 min on 2026-07-27 (10:07-10:50 AM)** (https://github.com/jdeath/Hubspace-Homeassistant/issues/240)
- Hubspace app complaint rate (App-Store-derived tracker) = **70 reports/24 h: 27.0% connection, 19.8% not working, 11.7% login** (https://justuseapp.com/en/app/1506042235/hubspace/problems)

## Bench tests
- Command RTT baseline: from the kiosk bridge on the venue-like network, send 100 single-bulb PUTs (one bulb, randomized colors) via aioafero 9.3.0 and measure (a) HTTP accept latency and (b) tap-to-visible-change with a phone camera at 240fps or a photodiode; report p50/p95/p99 against the <2s visible-start target.
- Fan-out spread test: fire 40 concurrent PUTs (one zone) with stock TCPConnector(limit_per_host=3), then rebuild the session with limit_per_host = 10 / 20 / 40 and repeat; measure first-to-last-bulb spread each way and record any 429/503/500 responses or degraded payloads — this single test decides whether one account can meet the <2s spread target or the build needs 5 accounts.
- Rate-limit threshold probe (do this on a burner account first): sustain 1, 2, 5, 10, 20 req/s of state GETs+PUTs for 10 min each; log first appearance of 429/503, response-field degradation (the community-observed 'lost device names' symptom), and cool-down time to normal service; then repeat the same ramp on two accounts simultaneously from the SAME public IP to determine whether throttling is per-account or per-IP (decides if 5 zone-accounts actually multiply throughput at the venue NAT).
- Conclave feedback latency: run bridge with enable_conclave=True, send a PUT, timestamp the corresponding attr_change push arrival; 100 samples for p95 — validates using push events as the kiosk's 'scene applied' confirmation instead of polling.
- 8h soak at show scale: 200 bulbs across 5 accounts (5 bridge instances), scene change every 60-90s, Conclave on, REST true-up 900s; monitor per-account token refreshes (~every 116s each), Conclave reconnect counts, command queue depth, memory, and total bandwidth (compare against the ~87KB/poll figure from issue #216) — verifies zero queue growth and no cumulative throttling.
- WAN-cut recovery: pull the venue uplink for 2, 10, and 30 minutes mid-show-loop; verify Conclave reconnects (fresh conclaveAccess token, backoff capped at 60s) and first successful scene change within 60s of internet restoration; also verify bulbs' own behavior (do they hold last state?) since the cloud has no offline command queue you control.
- 429-response autopsy: when the probe finally triggers throttling, capture exact status codes, response headers (Retry-After?), and body — no public source documents what Afero's throttle response actually looks like, and the bridge's retry logic should key off the real signal rather than aioafero's blind 0.25s-step retries.

## Open questions
- What is the actual numeric rate limit (requests/min) per account, and is there an additional per-IP limit? Nothing public exists — only the 2s polling floor (Emkraan) and 10s-polling degradation (July 2025 report). The 200-PUT scene burst is far outside any publicly tested envelope.
- Does any server-side group/scene primitive exist in the Afero API (apply one command to N devices)? aioafero exposes only per-metadevice state PUTs; if the official app's 'groups' are client-side fan-out too, nothing saves you from 200 calls — needs MITM capture of the official app applying a group scene (aioafero docs include a MITM capture guide).
- Is Afero throttling keyed to account, OAuth client, token, or source IP? Determines whether Home Depot's separate-accounts-per-vignette advice actually multiplies aggregate throughput from one kiosk NAT.
- What is real Conclave push latency (ms) under load, and does it degrade during command bursts? No public measurements exist at all.
- How does the largest publicly-known account (~14-50 devices) compare to 40-200 devices per account — does poll payload size or command acceptance degrade nonlinearly with device count?
- Was Hubspace affected by the 2025-06-12 Google Cloud outage (relevant since DNS proves Afero is GCP-hosted, and the Oct 20 2025 AWS outage was likely a non-event for them)? Search budget ran out before confirming; worth one check.
- Why did the July 2026 incident (issue #240) resolve — Afero-side fix or client fix? The issue closed without a documented root cause, so mean-time-to-recovery for Afero cloud incidents is unknown.
